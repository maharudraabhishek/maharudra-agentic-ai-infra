## Changed

- `AgentOrchestratorOptions.multiAgentExecutor` is now required so the runtime container can wire the forward-compatible multi-agent executor dependency in the next phase.
- `AgentOrchestrator.run()` now executes supervisor plans by composition:
  - `single` preserves the Phase 03 direct single-agent path.
  - `sequential` runs one `singleAgentExecutor.execute()` sub-run per planned agent through `runWithRetry()` and prefixes later tasks with prior role summaries.
  - `parallel` runs one retried single-agent sub-run per planned agent through `Promise.allSettled`, keeps partial success as `ok` with warnings, and returns `fail` when all branches fail.
- `OrchestratorReport.tokenUsage` now aggregates successful composed sub-runs for sequential/parallel routes.
- `OrchestratorReport.response` is populated only when the first planned agent has a response policy whose `guardTiming` is not `"per-agent"`; otherwise the optional field is omitted.

## Notes

- The executor-per-composition choice is intentionally conservative: sequential and parallel use the single-agent execution port for every planned agent so each `AgentDefinition.retryPolicy` is visible to `runWithRetry()`.
- The injected `TokenEfficientMultiAgentExecutor` is deliberately not invoked in this phase. It exists on the options and orchestrator instance for container wiring and future homogeneous role fan-out.
- The merged output guard builds a real `DeterministicAgentOutput` shape with `role: "manager"`, merged summary text, aggregate token usage, context source count, and citations derived from the supplied context package when present. It does not use `as any`.
